# ВГСПУ Расписание Бот

Telegram-бот расписания студентов ВГСПУ. Расписание берётся с `portal.vspu.ru`, выбранная группа, история активности и кэш вчерашнего дня хранятся в PostgreSQL.

## Запуск

Требования: Python 3.12+, PostgreSQL, токен Telegram-бота.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
```

Скопируйте `.env.example` в `.env`, задайте `BOT_TOKEN`, `DATABASE_URL` и при необходимости `ADMIN_IDS` (Telegram ID администраторов через запятую). Токены и пароли в Git не добавляются.

```bash
python -m src.main
```

Docker:

```bash
docker build -t vspu-schedule-bot .
docker run --env-file .env vspu-schedule-bot
```

Бот использует polling: для одного токена запускайте один экземпляр. Точка запуска регистрирует сообщения, callback-кнопки и inline-запросы. Для inline включите этот режим в BotFather. Очевидные запросы «сегодня», «завтра», «эта неделя» работают без внешнего ИИ; для свободных формулировок можно задать `DEEPSEEK_API_KEY` и `DEEPSEEK_MODEL`.

## Если расписания нет

Отсутствующая страница или ответ «Расписание не найдено» показываются как: «К сожалению, на портале ВГСПУ нет расписания твоей группы на выбранную неделю. Возможно, оно появится позже». Это работает при вводе группы, просмотре, обновлении, через быстрые кнопки и inline.

Пустая опубликованная таблица считается неделей без занятий. Таймауты, сетевые ошибки и ошибки сервера показываются отдельно как недоступность портала. Отсутствующее расписание не кэшируется; после публикации следующий запрос снова проверит портал. Проверка новой группы смотрит текущую, две следующие и предыдущую недели; если расписания нет нигде, код группы можно ввести позже. Успешное расписание кэшируется на `CACHE_TTL` секунд (по умолчанию сутки).

## Аналитика

Доступна администраторам через `/stats`, в веб-админке и в JSON-отчёте:

```bash
python check_db.py
```

Для веб-админки задайте `ADMIN_PASSWORD` и случайный `ADMIN_SECRET_KEY`, затем запустите отдельный процесс:

```bash
uvicorn admin.app:app --host 127.0.0.1 --port 8000
```

Публикуйте админку через HTTPS: cookie авторизации имеет флаг `Secure`.

Все интерфейсы используют одинаковые определения метрик:

| Метрика | Определение |
| --- | --- |
| DAU / WAU / MAU | Уникальные пользователи за сегодняшний / последние 7 / последние 30 календарных дней, включая текущий |
| Новые пользователи | Первое наблюдаемое действие попало в соответствующий период |
| Вернувшиеся сегодня | Активны сегодня, первое действие было до сегодняшнего дня |
| Retention D1 / D7 / D30 | Возврат ровно на N-й календарный день после первого действия; в знаменателе только пользователи, чей день возврата уже полностью закончился |
| DAU/MAU | Доля месячной аудитории, активная сегодня |
| Выбор группы | Доля наблюдаемых пользователей с сохранённой группой |
| Действий на DAU | Сообщения, нажатия кнопок и inline-запросы за сегодня / DAU |
| Неактивны 30 дней | Последнее действие было раньше начала 30-дневного окна |
| Запросы расписания | Успешные результаты, отсутствие на портале и технические ошибки за 30 дней |

Дни и когорты определяются по `Europe/Moscow`, временные метки в БД хранятся в UTC. Отсутствующий знаменатель отображается как «нет данных» / «—», а не как 0%.

Таблицы: `users` (группа), `user_activity` (журнал событий), `user_stats` (первое/последнее действие, счётчики), `user_daily_activity` (одна строка на пользователя и день), `schedule_cache`, `schema_migrations`. Счётчики обновляются атомарно, параллельные запросы не теряются. Результаты запросов расписания не увеличивают DAU повторно. Сбой записи аналитики логируется и не мешает выдаче расписания. Новые произвольные тексты сообщений в аналитику не записываются.

В админке есть дневные когорты с D1/D7/D30, активность по дням и распределение по группам. Retention отражает доступную историю наблюдений: восстановить действия до начала ведения журнала невозможно. События результатов расписания собираются после установки этой версии; старые результаты не выдумываются.

## Обновление существующей базы

Остановите старый процесс бота и запустите новую версию с прежним `DATABASE_URL`. При запуске бота или админки автоматически выполняется транзакционная миграция с блокировкой PostgreSQL и отметкой версии:

- создаётся дневная таблица активности, история заполняется из существующего `user_activity`;
- удаляются настройки `users.notifications_enabled` и `users.reminder_minutes`;
- пользователи, группы и история активности сохраняются;
- старые таблицы `reminder_deliveries` и `user_screens`, если были, остаются как неиспользуемый архив; новый код их не читает и не создаёт.

Уведомления, планировщик, обработчики и кнопки удалены. Миграция повторно не переносит историю. `check_db.py` только читает данные, поэтому перед его использованием новая версия должна хотя бы один раз выполнить запуск и миграцию.

## Проверки

```bash
pip install -r requirements-dev.txt
python -m pytest -q
ruff check src admin tests check_db.py
```

По умолчанию тесты используют временную SQLite. Для дополнительной проверки PostgreSQL задайте `TEST_DATABASE_URL=postgresql+asyncpg://...`: тесты создают отдельную случайную схему для каждого сценария и удаляют её после проверки. Пользователь тестовой БД должен иметь права создания схем. Проверяются миграция старой базы, перенос истории, повторный запуск, конкурентные счётчики, календарные границы retention, отсутствие расписания, сетевые ошибки, кнопки, inline и доступ к админке.
